# 审批交互重设计

## 意图与原因

手机 QQ 上处理审批最大的痛点是**要复制粘贴 10 位 id**。审批本身并不烦，烦的是输入方式，以及提示里只有工具名和参数、看不出这次调用到底想干什么、为什么要做。同时，连续有几个请求时会一条条轰炸，处理起来零碎。

目标是把审批变成：**看得懂 + 一个数字回复完 + 能批量 + 能给常用操作开免问**。

## 目标

1. 审批提示先给「要做什么 / 为什么」，由模型生成，失败自动降级。
2. 单条请求用数字选择：同意 / 拒绝 / 5 分钟内同类免问 / 以后同类免问。
3. 多条请求先汇总，给「全部同意 / 全部拒绝 / 详情」；选详情后按权限类型分组再问。
4. 免问授权按**会话**隔离，可查询、可撤销，并写入长期记忆。
5. 高危工具（sensitive / dangerous）在提示里加醒目提醒。

## 非目标

- 不做 WebUI 审批界面改版（沿用现有 `POST /api/approvals/{key}`）。
- 不改变自动审批（决策模型 / 文本模型复核）的判定逻辑，只改「人工审批」这一段。
- 不做跨设备的授权同步。

## 反目标

- 批量交互不能让「全部同意」顺带批掉之后才到达的请求——批量作用域在发出清单时就冻结。
- 超时后不能因为批量状态残留而执行任何东西。
- 免问授权不能泄漏到别的会话（群 / 网页 / 他人私聊）。

## 用户已确定的

- 「此类」= **同一个工具**（例如 shell 算一类）。
- 免问授权**按会话隔离**：主人私聊里放行 shell，群里和网页端不受影响。
- 授权可以事后**查看和撤销**，用一条查询命令即可。
- 高危工具**加提醒就行**，不必禁止提供免问选项。
- **含密钥文件的 shell 命令不可免问**：命令里出现 `config.toml`、`master.key`、`web.token`、`.credentials`、`state.sqlite3`、`profiles/` 时，永远是「问人一次」，5 分钟和永久免问都不覆盖它（这类命令原本就可能把密钥读进对话）。

## 我定的（builder 可调整，但要在实现说明里写清楚原因）

- **回复用数字**：手机上一个字符就能回。同时保留已有的纯文字「同意」「拒绝」。
- **说明由 `light` 路由生成**：两行，一句做什么、一句为什么；预算 2 秒，超时或失败降级为「工具名 + 参数摘要」。生成失败不影响审批本身。
- **批量收集窗口 2 秒**：第一条请求出现后等 2 秒，把这段时间内进来的请求合成一条清单。
- **5 分钟免问是内存态**：键为 (会话, 工具)，5 分钟后自动失效，不落盘、不进记忆。
- **永久免问落在三处**：`policy.sessions[会话].tools[工具] = "allow"`（真正生效）、一条 `approval_grant` 记录（查询与撤销的数据源）、一条长期记忆事实（让机器人在对话里记得给过这个权）。
- **权限类型分类用风险等级**：安全 / 一般 / 敏感 / 危险，同级内按工具名排序。
- **每屏最多列 5 条**：超出部分提示「还有 N 条」，处理完再看，避免手机上一屏刷屏。

## 交互形态

### 单条

```
需要确认：shell
要做：看一下仓库有没有未提交的改动
为什么：你刚问代码有没有存，我需要 git status 才能回答
回数字：
1 同意
2 拒绝
3 五分钟内 shell 都同意
4 以后 shell 都同意，不再问（⚠ 高危，慎重）
```

高危提醒的那一行只在风险等级为 sensitive / dangerous 时出现。

### 多条

```
有 3 条待确认：
1. shell（敏感）— 删除临时文件
2. shell（敏感）— 查看 git 状态
3. qq_message_send（一般）— 给某人发一条消息
回数字：
1 全部同意   2 全部拒绝   3 看详情
```

### 详情（按类型分组）

```
详情，按类型分：
[敏感 · shell] 2 条
[一般 · QQ] 1 条
回数字：
1 shell 全部同意   2 shell 全部拒绝
3 QQ 全部同意      4 QQ 全部拒绝
5 逐条处理
```

选 5 后逐条给出单条菜单（每条 1–4），处理完再发下一条。

## 会话归属

- 审批提示一律发到主人私聊（沿用 `notify_owner`），但**批次、5 分钟免问、永久授权都记在请求来源的会话上**（`private:…`、`group:…`、`web:…`），跟提示出现在哪个窗口无关。
- 同一个聊天同时只保留**一套**菜单。上一批没处理完时，新到的请求先排队，当前批次关闭后再发一张新清单；不在同一聊天里并发两套数字菜单。
- `background:*` 会话（主动任务、子代理）没有可写的会话策略，**只给「同意 / 拒绝」两种选择**，不提供免问；其审批仍走原有超时。

## 状态

- 每个来源会话最多一个活动批次：`{会话, 冻结的 key 列表, 创建时间}`，放内存。
- 批次里所有 key 都处理完（或全部超时）即清空。
- 批次冻结后新到的请求**不并入**，进入该聊天的排队区，等当前批次关闭后再成批发出。
- 任何未处理的 key 走原有 600 秒超时逻辑，超时即失效；进程重启直接丢弃批次状态。
- 菜单有效期 = 冻结的 key 全部处理完或超时。菜单打开期间，不是合法选项的消息照常进入正常对话，不吞消息。

## 数据

- `approval` 记录增加字段：`reason`（模型生成的两行说明）、`batch`（所属批次 id）、`risk`（生成时的工具风险等级）。
- 新增记录类型 `approval_grant`：`{会话, 工具, 风险, 说明, 时间}`，作为查询和撤销的数据源。

## 命令

- `/grants` — 列出当前会话的免问授权（工具、风险、授权时间、当时的原因）。
- `/grants 撤销 <工具>` — 撤销该会话的免问授权，同时把策略改回 `manual`、在记忆里补一条「已撤销」。
- `/approve`、`/deny`、纯文字「同意」「拒绝」保持不变。

## 约束

- 菜单交互只在 QQ 里生效；WebUI 继续用原来的 `POST /api/approvals/{key}`（以及页面上的按钮），不改。
- 只有主人在私聊里能审批；群聊和网页端各自独立，互不影响。
- 审批有效期沿用 `policy.approval_timeout`（默认 600 秒）。
- 免问授权只在「本来是 manual、要问人」这一步生效；模式、`denied_tools`、`scope_tools` 等拒绝性规则仍然优先。

## 留给 builder

- 批量清单里各条的顺序与编号规则（建议按风险等级从高到低）。
- 说明生成的具体 prompt 与超时后的降级文案。
- 授权写入长期记忆时的 `save_fact` 证据文本怎么取（数字回复不构成 turn）。
- 新增命令是否与现有 `/tools` 合并展示、是否加中文别名。
